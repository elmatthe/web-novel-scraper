# webnovel-scraper - 0.2.1 Release Plan
**Status:** Phase A complete; Phase D complete; Phase E complete. Phase B/C/F not yet run.
**Type:** Minor bug-fix release on the existing 0.2.0 framework.
**Scope:** Verify/stress the Phase C (BUG-1/2/3) fixes that 0.2.0 live-test data did NOT
exercise, plus a Codex-led general bug hunt across the codebase. **No new features.**

## 0. Explicit Non-Goals
- **No multi-worker / 1-5 rescue-lane toggle.** That work is explicitly deferred past
  0.2.1 per `Briefing.md` Next Steps and stays out of this plan entirely - single-lane
  `RESCUE_MAX_WORKERS = 1` is untouched.
- No new adapters/sites (`empire_novel`, `novel_bin`, `telegraph` stay disabled stubs).
- No GUI redesign. The one cosmetic item below (checkbox rename) is the only UI touch.
- No architecture changes. This is a bug-fix/hardening pass on the framework as it
  exists at 0.2.0, not a feature release.

## 1. Why 0.2.1, and what triggered it
The 2026-06-30 live test (1-3072 chapters across two runs, full log reviewed) was
**100% clean: 0 failures, 0 skips, all camoufox fetches succeeded on attempt 1/2.**
That's good news for the happy path, but it means three things shipped in 0.2.0's
Phase C were never actually exercised by a real failure condition:

| ID | What it fixes | Why the live test didn't prove it |
|---|---|---|
| BUG-1 | Camoufox page-closed liveness check + within-attempt recreate (`request_manager.py`: `_page_is_alive`, `_ensure_camoufox_page`, `_fetch_camoufox_once`) | No page ever closed mid-run - every fetch cleared cleanly, so the recreate path never fired. |
| BUG-2 | Cancel-aware sliced backoff (`_cancellable_backoff`) + atomic PDF writes (`pdf_builder.py: _atomic_write`) | No Stop was pressed; no write was interrupted; nothing ever needed to back off (no rate-limit/retry rungs were hit). |
| BUG-3 | Headful camoufox stalls while unfocused (Windows timer throttling) - documented, not code-fixed; BUG-1's recreate is the real mitigation | No stall occurred; the regression watch-list chapters (102, 175, 233, ..., 3062) were all fast first-try clears this run. |

All three have offline test coverage (`test_bug1_camoufox_liveness.py`,
`test_bug2_cancel_atomic.py`) but **zero live confirmation**. 0.2.1's first job is to
either trigger these conditions for real, or knowingly accept the offline coverage as
sufficient and move on - not let them sit as an open question forever.

### Phase B - Trigger BUG-1/BUG-3 for real (live reproduction)
Goal: stop relying on offline fakes for the camoufox-closed-page path - force the
condition live at least once.
- Candidate methods to explore (pick what's practical, document what was tried):
  1. **Minimize/occlude the browser window mid-run** on a known-slow chapter range
     to reproduce the Windows background-throttle stall (BUG-3) and confirm BUG-1's
     recreate logic actually fires and recovers within the same rung.
  2. **Force a real page close**: manually close the camoufox window mid-fetch (or
     kill the Firefox process) during a run and confirm the next fetch attempt
     recreates the page instead of hanging/failing the whole ladder.
  3. **Run the regression watch-list chapters specifically** (102, 175, 233, 268,
     271, 278, 307, 330, 334, 379, 403, 489, 508, 517, 518, 534, 546, 587, 629, 633,
     642, 715, 853, 860, 951, 998, 1039, 1251, 1521, 1897, 2018, 2142, 2420, 2817,
     3019, 3062 - the same list from the 0.2.0 plan) with **cache OFF**, since these
     previously needed rescue/escalation and are the most likely to reproduce a
     genuine closed-page event.
  4. If none of the above reproduces it live, **document that explicitly** as a
     known limitation (offline-only coverage, accepted) rather than leaving it silent.
- Deliverable: a short live-test log + a paragraph in `handoff.md` recording what was
  tried and the outcome (reproduced-and-recovered / not reproduced / accepted-as-is).

### Phase C - Trigger BUG-2 for real (Stop + atomic write under failure)
Goal: same idea, for the cancel/atomic-write fix.
- Candidate methods:
  1. Start a run on a long chapter range and **press Stop mid-backoff** (e.g. during
     a rate-limit retry) - confirm the app exits within ~0.25-0.5s instead of waiting
     out the full backoff window (this is directly observable: time the Stop-to-quiet
     latency).
  2. Press Stop **mid-PDF-write** (kill the run or close the window while a chapter
     is being written) - confirm no corrupt/partial PDF and no leftover `.part` file
     in the output folder afterward.
  3. If a rate-limit/retry rung never naturally triggers on a clean host, consider a
     deliberately tiny `Delay between fetches` + a chapter range likely to trip the
     host limiter, to force a backoff window worth cancelling out of.
- Deliverable: timing notes + output-folder inspection (no `.part`, no truncated PDF)
  recorded in `handoff.md`.
