## A. New Findings From This Hunt

### BH-1 - Major - `pipeline.py` trusts any output-dir `chapter_index.json`
- Location: `scripts/Universal/webnovel_scraper/pipeline.py:293-324`, `scripts/Universal/webnovel_scraper/pipeline.py:964-975`, `scripts/Universal/webnovel_scraper/pipeline.py:1219-1232`
- Actual behavior: `_save_index` writes only chapter rows (`index`, `url`, `title`, `source_id`), and `_load_index` accepts any non-empty list in the chosen output folder. The rescue path and legacy path both load that file before asking the current adapter/site to build a TOC.
- Why it matters: If the user intentionally or accidentally reuses an output folder for a different novel/site, the run can fetch URLs from the previous novel while naming output with the current novel. In `SINGLE`/`CHUNKED` mode, an existing PDF can also cause a whole current range to be skipped because the stale index defines the range.
- Repro/confirmation path: Run one novel into a folder, then construct a second `ScrapeJob` for another enabled novel using the same `output_dir`; observe that `adapter.build_chapter_index` is not called and URLs from the old `chapter_index.json` drive the run.
- Proposed fix direction: Add identity metadata to the persisted index (`novel_slug`, `adapter_key`, source URL/base URL, possibly a schema version) and ignore/rebuild the index when it does not match the current `ScrapeJob`/`SiteSpec`. Keep same-folder resume when the identity matches.

### BH-2 - Major - cached Cloudflare challenge HTML is returned as a cache hit
- Location: `scripts/Universal/webnovel_scraper/request_manager.py:753-769`, `scripts/Universal/webnovel_scraper/request_manager.py:995-1000`
- Actual behavior: `_read_cache` self-heals garbled brotli-era cache entries, but it does not reject a cached Cloudflare interstitial. `_fetch_with_retry_ladder` returns any accepted cached text before body-first challenge classification runs.
- Why it matters: A stale challenge page left by an older build or a manual cache copy can bypass all current retry/rescue logic. The adapter then sees a fetched-but-empty page and records an extraction failure instead of re-fetching/rescuing the chapter.
- Repro/confirmation path: Write a known Cloudflare challenge fixture to `RequestManager.cache_path_for(url)` with cache enabled, then fetch the same URL. Confirm the manager returns the cached challenge without calling `_fetch_uncached_strategy`; then route it through `FreeWebNovelAdapter.fetch_chapter` and observe `EmptyExtractionError`.
- Proposed fix direction: Treat cached active challenges like garbled cache entries: log, ignore the cache hit, and re-fetch. Use the shared `is_cloudflare_challenge` detector after the garbled check; real payload remains accepted because the detector is payload-gated.

### BH-3 - Minor - `HostRateLimiter` FIFO is global, not per-host
- Location: `scripts/Universal/webnovel_scraper/host_rate_limiter.py:93-96`, `scripts/Universal/webnovel_scraper/host_rate_limiter.py:153-178`
- Actual behavior: The limiter has one `_waiters` deque for all URLs. A waiter for host B cannot proceed while a host A waiter is at the front waiting for host A's interval/cooldown, even if host B has no cooldown and is immediately eligible.
- Why it matters: The module docstring promises per-host pacing and says other hosts are not blocked by one host's wait. Current production runs usually target one host, so the blast radius is small today, but the implementation is more serial than documented and could create surprising stalls for mixed-host flows.
- Repro/confirmation path: In a threaded test, first reserve or cool down host A, then start one waiter for A and one for B. Observe B stuck behind A until A's front ticket completes.
- Proposed fix direction: Make the waiter queue per normalized host, or keep a global condition with per-host deques so FIFO fairness applies within a host rather than across unrelated hosts.

### BH-4 - Minor - README delay default was stale
- Location: `README.md:50-53`, `scripts/Universal/app.py:41-45`
- Actual behavior: README said the default delay was 2 seconds, while the GUI constant is `DEFAULT_DELAY = "3.0"` and `request_manager.DEFAULT_DELAY` is `3.0`.
- Why it matters: This is user-facing configuration drift; it can confuse manual live-test instructions and expected scrape timing.
- Repro/confirmation path: Open the GUI or inspect `app.DEFAULT_DELAY`; compare to README's "2 seconds" sentence.
- Proposed fix direction: Update README to say 3 seconds. This docs-only correction was applied during Phase A.

### BH-5 - Suggestion - `RescuePool.start()` is not synchronized against concurrent starts
- Location: `scripts/Universal/webnovel_scraper/rescue_pool.py:254`, `scripts/Universal/webnovel_scraper/rescue_pool.py:277-281`
- Actual behavior: Constructor validation enforces `workers == RESCUE_WORKERS == RESCUE_MAX_WORKERS == 1`, and the pipeline calls `_ensure_pool().start()` from one conductor thread. However, `start()` itself checks `self._thread is not None` without a lock, then assigns and starts the thread.
- Why it matters: I did not find a current production path that calls `start()` concurrently, so the 0.2.0 single-lane invariant holds in the live conductor. As a public lifecycle method, though, two racing callers could both observe `_thread is None` and create two worker threads on one pool.
- Repro/confirmation path: Stress a single `RescuePool` instance with two threads calling `start()` at the same time, with `threading.Thread` monkeypatched/spied to widen the race window; confirm whether two start calls can be issued.
- Proposed fix direction: Guard `start()` with `self._lock` or a dedicated start lock, and keep the current idempotent return behavior.

### BH-6 - Suggestion - GUI lifecycle docstrings still say daemon thread
- Location: `scripts/Universal/app.py:1-7`, `scripts/Universal/app.py:75-76`, `scripts/Universal/app.py:528-534`
- Actual behavior: The implementation creates the worker with `daemon=False` and the close path polls until it exits, but the module/class docstrings still describe a daemon worker.
- Why it matters: Runtime behavior is correct; this is stale developer-facing documentation and can mislead later lifecycle work.
- Repro/confirmation path: Inspect `threading.Thread(..., daemon=False)` in `_on_start` and compare to the docstrings.
- Proposed fix direction: In Phase D/E docs cleanup, change the docstrings to "non-daemon worker thread" and mention the poll-until-exit close path.
